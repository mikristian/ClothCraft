### The key CLO point-type distinction

An **outline/segment vertex** is a topological node on the boundary. It carries sewing and notch relationships between its two outgoing/incoming edges. A **free curve point** can reshape the curve within a boundary without necessarily being the same topological cutline split. A **Bézier control handle** shapes the incoming/outgoing cubic tangent of an anchor; dragging it does not add a cut vertex. The tools above address different objects. Treating every click as the same kind of editable point creates false split seams and makes grading and notches unstable.

The loaded CLO screenshot shows actual neckline Bézier handles with colored control points and two measurements: **17.00 cm 2D versus 16.95 cm 3D** for the one side; a **34.00 cm symmetric measurement** appeared in the Property Editor. Dragging the control changed the visible 2D curve to **17.51 cm**. EXO needs to keep planar material arclength, symmetric linked length, and simulated/draped 3D length as separate values, even when the same selected edge underlies all three.

## EXO implementation audit — exact code evidence

1. **Tool granularity, P0.** `src/components/ClothCraftBoardV2.jsx` currently maps `tool2d` values `select`, `point`, `curve`, `split`, etc. to broader editing modes (near lines 445–466). A single `'curve'` branch selects edge handles, moves pattern anchors, alters internal-line tangents and creates cubic handles on click (near 1370–1390, 1490–1565). There is not yet a separate native equivalent of CLO's *Edit Curvature segment pull* versus *Edit Curve Point free point insertion* versus *Bézier tangent handle* selection. Split is a separate tool, which is a good starting boundary. **Acceptance:** distinct tool states, distinct control point shapes, context menu and accessible hit targets; clicking free curve point must not create an outline vertex.
2. **Modifier mismatch, P0.** `src/core/vectorPatternBezier.js` and `ClothCraftBoardV2.jsx` currently expose Alt to break tangents and **Shift to snap the handle angle to 45°**. CLO's Bézier documentation describes **Cmd on Mac to preserve handle angle** while dragging, and Alt to edit one side independently. These are not identical; users expecting CLO muscle memory will get different tangent behavior. **Acceptance:** add a CLO modifier preset with explicit semantics and test on a straight, smooth, and corner anchor. Preserve optional VectorCraft controls as a separately labeled preset.
3. **Cutline split topology, P0.** The current board's `splitBoundary` projects a click onto the sampled edge and issues a single `SplitBoundary { panel, edge, at_m }` native Rust command (`ClothCraftBoardV2.jsx`, near 980–1005). The Rust implementation `research/oss/clothcraft/src/authoring.rs`, lines 866–945, maintains exact cubic split geometry but deliberately refuses seam-connected edges, edges with target length, and edges with notches or seam allowances. That fails CLO's full practical workflow when a sewn production pattern is refined. **Acceptance:** support numeric arclength, ratio, N-way subdivision, Smart Guide hit points and complete stable edge-reference migration with Undo. Keep the documented fail-closed behavior until that migration is reliable.
4. **Measurements, P0.** `ClothCraftBoardV2.jsx` uses `cubicLength` in metres and renders a currently selected cubic preview label in cm (`data-native-cubic-length-cm`, near 1520–1540). The entire line-selection sidebar does not yet surface the three distinct observed CLO quantities as a coherent point/edge property. `src/core/clo7NativeToolCapabilities.js` already correctly distinguishes actual sewn-edge walk with 2D and 3D length from simple temporary measurement. **Acceptance:** on selecting any outline/internal segment, recompute real 2D arclength and, when linked, its symmetric sum and current 3D draped result with explicit simulation revision. A handle movement must recompute it live; no chord approximation.
5. **POM persistence, P0.** `ClothCraftBoardV2.jsx` maintains two-point tape in local React `useState([])`; tool switches clear it, and render includes `data-tape-measurement` near line 1621. `src/core/clo7NativeToolCapabilities.js` explicitly calls this a temporary tape, not a saved graded POM. **Acceptance:** first-class `pom[]` records with ID, panel(s), ordered path segments and fractions, grouping, size-grading values, 2D/3D modes, display formatting, save/reopen and undo; segment/curve edits must reproject related POMs or warn/reject, never silently detach them.
6. **Transform point/segment, P1.** Current `Anchor` move supports pointer drag and preview in `ClothCraftBoardV2.jsx` (near 790–920), and native Property Editor permits numeric point coordinates. CLO's separate Transform Point/Segment tool also has a *pivot-controlled segment rotation and scaling marquee* with numeric dimensions. **Acceptance:** separate single segment transform operation with pivot, scale and rotation, zero distortion of untouched other segments, undo and clear dimensional readouts.
7. **Selection/hit testing, P1.** CLO supports selecting a point, line, and lasso of multiple items; its docs describe double-clicking the 2D window to activate lasso. EXO's native board currently emphasizes whole-panel selection and individually active points/curve handles; multi-point lasso and priority between overlapped anchors, handles and close boundary segments need parity testing. **Acceptance:** a zoom-independent pixel radius, handle-over-segment picking precedence, Shift multi-selection, temporary marquee, and no accidental drag of the entire panel when point tool is active.
8. **Internal curves, P1.** EXO `NativeInternalLines` already has tangents and visible curve previews, but it should distinguish free curve points, internal structural lines, baselines, grainlines and annotations with distinct selection/layer rules. **Acceptance:** every point action applied to an internal line preserves its semantic type, length and sewing linkage; do not silently convert guide art to a cutline.

## Additional exact Rust schema and behavior findings

The authoritative EXO Polygon serialization in `research/oss/clothcraft/src/garment/polygon.rs` contains `points: Vec<DVec2>`, exactly one stable string ID in `edges` per point, and `curves: BTreeMap<String, [DVec2;2]>` giving **two cubic handles per named edge**. It also stores internal `lines`, `notches` by edge ID, target lengths, allowances, and annotations. There is no separate persisted `free_curve_points` array or per-anchor semantic class, and no persistent typed graded POM path list. This source-level absence is more precise than saying that the UI simply fails to show certain buttons.

Rust `Command::CurvePoint { panel, anchor, curved }` in `research/oss/clothcraft/src/authoring.rs` lines 1011–1050 **toggles Bézier cubic handles on both outline edges incident to a topological anchor**. When `curved: true`, it creates collinear controls at one-third and two-thirds of the straight segment, preserving the geometry; when false, it removes those cubic controls. It does **not** insert or move CLO-style free curve points. Thus the existing native command is a useful *smooth/straighten existing cutline corner* primitive, yet should **not** be presented to users as an implementation of CLO's distinct `Edit Curve Point` tool. Implementing the latter requires a new typed non-cut vertex model or a curve-segment model that supports ordered intermediate shaping constraints without inventing sewing edges.

The next Rust command `SplitBoundary` does an exact de Casteljau cubic split at the physical arclength requested. It adds one point and a derived stable edge name; this is a real **topological split**, unlike a Bézier handle edit. `RemovePoint` preserves minimum count, refuses a sewn incident edge, checks target/notch/allowance attachments on either incident edge, and refuses to remove a point adjacent to any active Bézier controls. Production EXO already protects the geometry against dangling relationships but needs atomic remapping to support the full CLO workflow. The existing rigorous refusal is preferable to creating a false seam or silent data loss.

The current EXO 2D toolbar capability inventory in `src/core/clo7NativeToolCapabilities.js` contains **32 slots: 19 tagged `native`, 10 `inspect`, 3 `unavailable`** (Steam, Seam Taping, Set Sublayer). These flags describe available EXO actions, **not verified CLO equivalence**. For example, `Edit Point of Measure` and `Point of Measure` are both `inspect` and invoke only temporary tape measurement. The 2D A01/A02 select/edit slots are present, but the live verified CLO submenu's `Edit Curvature`, `Edit Curve Point`, `Add Point/Split Line`, and `Transform Point/Segment` have no separate first-class 2D toolbar slots in this list; a grouping UI or subtool flyout must retain these names and behaviors.

## Read-only ZPAC fixture container evidence

Offline inspection of the unmodified 912,850-byte disposable `.zpac` sample found a **CLO-proprietary leading data header followed by a readable ZIP directory**. `unzip -l` reported 154,578 extra bytes before/within the ZIP archive and five embedded entries:

| Embedded file type | Uncompressed size | Purpose inferred from filename only |
| --- | ---: | --- |
| `.pac` | 7,194,741 bytes | Native garment/pattern document; proprietary structured binary |
| Two `.jpg` images | 21,744 and 172,638 bytes | Stitch/puckering image assets |
| One `.png` image | 66,359 bytes | Seam puckering image asset |
| `clofiles.json` | 562 bytes | Archive contents/source path manifest |

The `.pac` bytes contain many human-readable internal names mentioning pattern, curve, line, point, seam and notch, but no straightforward XML/JSON pattern or external documented `PointType` table. **No native point coordinates, curve handles, sewing rules or manufacturing dimensions were recovered reliably** from those binaries. A ZIP listing is evidence of packaging, not a supported geometry importer or proof of CLO's point implementation. Neither sample nor asset bytes are redistributed outside the private research workspace.

For reproducible interchange, CLO documents the supported `File > Export > DXF` path, with AAMA/ASTM or standard DXF, explicit measurement units, optional grading/annotations and cutting-versus-sewing-line semantics: [2D Pattern (DXF) Import/Export](https://support.clo3d.com/hc/en-us/articles/115000493067-2D-Pattern-DXF-Import-Export). CLO also documents `File > Export > Adobe (PDF)` for planar outputs: [2D Pattern (AI/PDF) Import/Export](https://support.clo3d.com/hc/en-us/articles/115004273427-2D-Pattern-AI-PDF-Import-Export). The live CLO menu previously exposed both entries. Future measured baseline comparisons should use a native exported **DXF-AAMA / DXF-ASTM** or PDF produced from a healthy test document, preserving declared unit, cutting/sewing designation and grading; do not pretend the `.zpac` binary is an interoperable JSON pattern.
