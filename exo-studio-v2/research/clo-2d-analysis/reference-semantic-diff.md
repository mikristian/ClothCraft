## Judgment: probably the **back bodice** (~85% confidence)

1. **Shallow curved neckline:** the crop shows a single center-neck low point around `(347,297)` with neck/shoulder transitions around `(230,261)` / `(463,261)`; the ~36 px neckline drop is only ~4% of the ~885 px neck-to-hem height. The **legacy back** has shallow neck center `y=67` relative to shoulder height `y=71` (~4/71), while **front** has center `y=63` (~8/71): `defaultProject.js:242-270`. Pixel proportions are approximate, not aligned dimensional measurements, but strongly favor back.
2. **Paired underarm/armhole ticks:** two short, roughly parallel red strokes appear on **each** side near `(67,445)` / `(626,450)` (four strokes total). Legacy **front** notches are `type:'single'` on contour edges `2` and `6` (`defaultProject.js:307-309`); **back** notches are `type:'double'` on those edges (`:341-344`). This is the strongest independent signal for back. The marks lie near the *lower armhole/armscye edge*, not demonstrably on the long side seam below the armscye.
3. **Midline:** a vertical dashed center line runs from neck to hem and crosses transverse guidelines. This is consistent with center back, but a centered front can have the same guide; it does not discriminate by itself. Some colored/grey endpoints may indicate selections, so the crop does not verify actual fold, symmetry or grain behavior.

**Counterevidence/uncertainty:** both front and back use near-identical torso outlines in legacy EXO; the screenshot has no piece label or identifying measurement. CLO notches may be customized independently, so two red marks do not *prove* back. Native CLO validation: click the large pattern with Transform Pattern, read its **Name / Type** in **2D → Pattern Information** or Property Editor, inspect the neckline depth, and select a red pair with Notch versus Sewing tools. Until then label fixture `back-bodice-reference` / `probable back`, not “confirmed native back.” Official [Pattern Information](https://support.clo3d.com/hc/en-us/articles/59635504938777-2D-Pattern-Information), [Notch](https://support.clo3d.com/hc/en-us/articles/115015735467-Notch).

## Purple shoulder strokes: **internal offset/construction lines** are likelier than true seam allowances (~80% confidence)

There is one thin **purple stroke slightly inside and parallel to each shoulder edge**, connecting lavender ring endpoints near neck/upper outer shoulder. Similar purple transverse and lower hem strokes appear across the body, while the actual cutting outline is dark. Official CLO [2D Seam Allowance](https://support.clo3d.com/hc/en-us/articles/115015714428-2D-Seam-Allowance) describes *generated seam allowance* as **light grey**, owned by a pattern edge/internal line, with a width and join settings in [Seam Allowance Properties](https://support.clo3d.com/hc/en-us/articles/115015631887-Edit-2D-Seam-Allowance-Properties). CLO separately creates independent [Offset as Internal Line](https://support.clo3d.com/hc/en-us/articles/115012380888-Offset-as-Internal-Line) and [Offset Pattern Outline](https://support.clo3d.com/hc/en-us/articles/115012380908-Offset-Pattern-Outline), optionally preserving the former boundary as an internal line. The purple stroke is therefore more plausibly an **offset/internal construction guideline**, although its exact meaning is unknowable from color alone. It could also be design/topstitch reference. Selecting the stroke and checking its Property Editor type and seam-allowance visibility are decisive.

**Implementation rule:** store a shoulder internal line (`internalLine`, parent piece/edge + physical offset/reference geometry) separately from an allowance (`seamAllowance` width/edge joins) and from topstitch (`topstitch` style + interval). Never set a real 1-cm seam allowance solely because a purple parallel stroke is displayed. Current V2 visual code `ClothCraftBoardV2.jsx:109-123` explicitly calls this a `shoulder-offset-reference`, paints it purple and **suppresses it when a native seam allowance exists**: that is evidence this *EXO representation* is visual and not a native allowance, not evidence of what native CLO originally selected.

## Red pair: **physical double notches** likelier than directional sewing indicators (~85% confidence)

The image shows two short red marks per lower armscye, approximately parallel and crossing outward from the outline. This matches a **double sewing alignment notch**, commonly used here to differentiate back from front. Official [Notch](https://support.clo3d.com/hc/en-us/articles/115015735467-Notch), [Create Notch](https://support.clo3d.com/hc/en-us/articles/115013214287-Create-Notch) and [Edit Notch Properties](https://support.clo3d.com/hc/en-us/articles/115015735687-Edit-Notch-Properties) document edge-attached, editable notch **Type, Angle, Flip, Length**. By comparison official [Segment Sewing](https://support.clo3d.com/hc/en-us/articles/115012381248-Segment-Sewing) and [2D Segment Sewing](https://support.clo3d.com/hc/en-us/articles/115000498767--2D-Tool-Segment-Sewing) use **directional notches** to indicate correspondence and seam orientation between **two sewn intervals**, and direction changes as mouse moves. The screenshot has no visible cross-piece sewing partner/connector or selected sewing pair, so **ordinary back double notches are the better hypothesis**; color alone is insufficient to establish object type.

**Implementation rule:** physical notch style and sewing orientation are **different data**. A double notch is one logical matching marker style rendered with **two slits** (or, for current Rust support, two tightly spaced `EdgeNotch` instances with a shared future `matchGroupId`); a directional sewing marker belongs to a directed `SeamSpec`/boundary pair and does not increase the cutting notch count. Current EXO overlay `ClothCraftBoardV2.jsx:124-155` draws red `data-2d-construction='notch-tick'` as SVG-only; it computes `count=2` by matching “back” in the panel name when no native notches exist. This is useful for appearance but is **not persistent native notch geometry**.

## Small top rectangle: probable separate neck binding / neck tape / rib strip (~65% confidence)

The upper element is a **separate narrow white horizontal piece** around `(232,160)` to `(462,180)` with dark perimeter, a marked center (`x≈347`) and small red end ticks. It is not connected to the main bodice in the image. Its length is similar to the projected width between neck points below, suggesting a **neck tape, back-neck facing, or neckline rib-band segment** prepared for sewing; it does **not** prove that this is the entire full-circumference collar band. CLO explicitly supports Pattern `Type` **Binding** and **Neck Tape** in [Pattern Information](https://support.clo3d.com/hc/en-us/articles/59635504938777-2D-Pattern-Information); community tutorials describe creating a rectangular [neck tape pattern with internal lines](https://support.clo3d.com/hc/en-us/community/posts/360003714187-How-to-express-Neck-Tape) or [straight strip sewn to neckline](https://support.clo3d.com/hc/en-us/community/posts/360027459034-Binding-inside-of-a-t-shirt). Those tutorials demonstrate feasibility, not the actual object type of this crop.

**Implementation rule:** keep it a separate named polygon/piece (`back-neck-tape` or `neckband-study`) with measured physical width/length and its own material, center reference and end/alignment notches; model its attachment with actual sewing edge pairs. Do not fabricate precise strip dimensions from screenshot pixels; do not automatically assign one strip to both front/back necklines without measured seam correspondence. Legacy `defaultProject.js:315-317,349-351` instead uses **edge-bound `bindings`** on front/back neckline and has **no independent strip piece**. That is a representation difference requiring an explicit conversion decision (materialized neckband piece vs finishing trim overlay).

## Recommended **shared reference sample**, without production edits

Keep a canonical garment sample **separate from the default simulation fixture** with `front`, `back`, `sleeve-left`, `sleeve-right` and `neckband-or-neck-tape` as independently identified pieces. Use mirrored left/right curves, a deliberately shallower back neckline, separate curved armholes, named edge IDs (e.g. `back-armhole-left-lower`, `back-armhole-right-lower`, `back-neckline`, `back-shoulder-left/right`), explicit per-edge sewing relations, and normalized **arclength-based** marker positions. Add persistent `constructionLines` for shoulder interior offsets, center-back dashed fold/reference, chest/belly widths, hem fold guides and any curved central mark; display types may be purple/dashed but semantics come from the selected object, not color. Attach **single notches to front armscyes** and **double notches to back armscyes**; match the front/back sleeve cap notches accordingly. Add a separate strip `back-neck-tape` only after confirming whether it is back tape or full neckband; attach center/end markers and seam pairing to the appropriate neckline length. Preserve actual seam allowance width/joins as separate edge properties, independent of purple interior line overlays. Persist units and selection metadata for comparison under different 2D zoom.

**Bridge recommendation:** legacy uses edge indices + notch type (`single`/`double`), while Rust uses named edges + `Vec<EdgeNotch{t,depth_m}>`; a future converter should map edge role by geometry/topology, **not numeric index equality**, and preserve semantic type/group in a metadata extension. Until native notch type is available, render two closely spaced Rust notch objects for back only, with stable group ID maintained in the bridge or fixture annotation, and don't claim that two independent objects equal complete CLO notch styling. Keep explicit `physical_notch`, `sewing_direction` and `decorative_reference_tick` categories. V2 currently draws decorative fallback marks and purple offsets; sample parity should test **actual native persistence** separately from screenshot styling.
