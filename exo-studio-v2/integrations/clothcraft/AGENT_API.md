# ClothCraft Native Agent API (v1.2)

The existing V2 bridge serves the agent API at `http://127.0.0.1:5385/agent/v1/` when `EXO_CLOTHCRAFT_PORT=5385`. The exact base port depends on the running server configuration. `GET capabilities` enumerates supported actions; `GET status` reports whether the native garment is loaded. `POST actions` accepts JSON `{ "action": "workspace.snapshot" }`, or `{ "action": "workspace.summary" }` for a concise readout of patterns, seams, fabrics, and graphics.

Mutation examples: `{ "action": "workspace.save", "expectedRevision": 12 }`, `{ "action": "workspace.undo", "expectedRevision": 12 }`, `{ "action": "workspace.redo", "expectedRevision": 13 }`, `{ "action": "simulation.pause", "expectedRevision": 14 }`, `{ "action": "simulation.step", "expectedRevision": 14, "steps": 1 }`, and `{ "action": "line.setTargetSpecification", "expectedRevision": 15, "panel": "front", "edge": "hem", "targetCm": 42 }`. Named edge measurements use `line.inspect` with `panel` and `edge`. Mutations reject stale revisions with HTTP 409. Fetch a new snapshot before retrying. Save persists the current native workspace in its configured output directory; arbitrary file paths and user-provided file uploads are intentionally unsupported by this agent interface.

`POST /agent/v1/batch` accepts `{ "actions": [ ... ] }`, with 1–16 individually validated action objects. Commands execute sequentially and stop at the first failure, returning `failedIndex`, `completed`, and step results. A batch is **not atomic** and has **no automatic rollback**. Specify the precise `expectedRevision` for each mutation, including changes made by previous steps; to avoid guessing revisions, submit mutations one at a time and read the returned revision. A single request is serialized against other agent calls. The browser's existing native `/workspace` channel remains separately usable by trusted local UI callers.

The HTTP server binds to IPv4 loopback (`127.0.0.1`) and keeps its origin allowlist. Set `EXO_AGENT_API_TOKEN` on the server to require an `X-ClothCraft-Token` header for all agent endpoints; use the same variable in MCP to forward that token. If enabled, the HTTP server's `OPTIONS` handler should include `X-ClothCraft-Token` in `Access-Control-Allow-Headers` **only for allowlisted Origins and agent API paths**. Keep `Content-Type` for ordinary routes; never allow wildcard origins or non-loopback binding. A CORS preflight does not authenticate the following request: the agent endpoint still checks the token on every actual request. Without a token, local processes and allowed browser origins can call the agent surface. The stdio MCP bridge is read-only unless launched with `EXO_MCP_ALLOW_EDITS=1`; it exposes `exo_capabilities`, `exo_status`, `exo_project_summary`, `exo_line_inspect`, `exo_workspace_save`, `exo_workspace_undo`, `exo_workspace_redo`, `exo_pause_simulation`, `exo_step_simulation`, and `exo_set_line_target`. MCP is a client of the already running HTTP service and cannot restart native Rust.

This API represents confirmed native operations only. Pattern authoring and graphics/material changes exist in lower-level Rust commands but require typed schemas before exposure as general-purpose agent actions. File open from arbitrary filesystem paths, an external cloud API, and a stable editor command bus are not claimed. The original `/workspace` HTTP route remains unchanged.

Verify: `node integrations/clothcraft/qa-v2-agent-api.mjs` and `node integrations/clothcraft/qa-v2-agent-automation-20261017.mjs`. The running service must be restarted by its owner to load an updated agent-api module.
