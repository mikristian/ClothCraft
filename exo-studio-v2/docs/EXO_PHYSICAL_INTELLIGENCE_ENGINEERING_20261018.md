# EXO Physical Intelligence Engine — first engineering loop

**Date:** 2026-10-18. **Scope:** physical validation and a correctness improvement to CPU VBD reporting. These checks are research and regression evidence; none establishes physical fit certification or manufacturer approval. No installed production application or saved user garment was modified.

## Baseline and architecture

EXO currently has several distinct physics pathways. The legacy JavaScript tee simulation in `src/core/physics.js` drives `scripts/check-avatar.mjs`. The ClothCraft Rust session supports an f64 CPU vertex-block-descent solver with OGC contact and a separate f32 GPU local solve with CPU OGC. The reference Rust Newton/PCG fitting solver is yet another path. `ppf_backend` runs a Blender/PPF integration and independent reported contact, strain, trajectory and IPC swept-CCD checks. JS avatar results must not be presented as equivalent to Rust or PPF results.

Running `node scripts/check-avatar.mjs` before this work gave these reproducible fixture outputs after 120 legacy JS frames:

| Avatar/garment | Average strain | Peak local strain | Mean seam gap |
| --- | ---: | ---: | ---: |
| Tee, 160 cm | 7.6% | 171.8% | 8.7 mm |
| Tee, 200 cm | 8.4% | 206.5% | 8.5 mm |
| Tee, modified upper body | 15.7% | 836.5% | 11.8 mm |

The last configuration has particularly high local deformation. The script's 250% peak-strain guard applies only to its first two configurations, so its zero exit status does **not** certify the modified-body fixture. The current measurements do not identify whether the root cause is the authored pattern, animation/collider geometry, initial arrangement, solver stiffness, or its contact model.

## Verified changes

1. **CPU VBD final-state stationarity metric:** `research/oss/clothcraft/src/vbd.rs` now calculates `residual_rms_n` from the **accepted final positions** for all unpinned degrees of freedom. Previously, it combined gradients sampled before successive color-group updates, which did not represent any single physical state. `tests/vbd_residual_contract.rs` independently differentiates the implicit-Euler objective and verifies the reported RMS. It passed with `cargo test --locked --offline --no-default-features -j 2 --test vbd_residual_contract`. The existing VBD suite passed 4/4. This improves the reliability of solver diagnostics; it is **not** a change to the constitutive law, contact forces or draped garment trajectory.
2. **PPF evidence validation:** `ppf_backend/fitAcceptance.mjs` now requires nonnegative integer collision/strain counts, finite per-frame principal stretch within its existing 5% engineering guard, nonnegative and ordered sewing mean/maximum gap reports, and matching frame coverage. `node --test ppf_backend/fitAcceptance.test.mjs` passed 2 tests (positive coverage and negative/corrupt report examples). This closes paths by which contradictory or invalid reports could have been accepted; it does not improve the actual PPF integration, collision geometry or cloth simulation.
3. **Reproducible native CPU lab:** `scripts/engineering/physics-lab-20261018/run.mjs` runs fresh native sessions with T-shirt, dress and repeat T-shirt configurations, records input binary/avatar hashes and per-step metrics, and emits `docs/physics-lab/baseline-cpu.json`. Read its README for limitations and the exact reproduction command.
4. **Isolated GPU smoke:** The already installed *QA* app contains an older executable with the desktop feature. An independent `--gpu` process completed one T-shirt simulation step, reporting the GPU VBD + CPU OGC path and reducing initial seam gap from 0.530 m to approximately 0.52461 m. Evidence is in `docs/physics-lab/smoke-gpu.json`. The QA executable's source revision is not attested to match the current CPU executable, so no GPU-versus-CPU speed or numerical-parity ratio can be reported.
   A same-source desktop-feature build was also staged through the Jarvis Expansion tunnel in a uniquely isolated source and target directory. Its arm64 cross-build could not be executed on Jarvis's x86_64 hardware, and an x86_64 native build was intentionally stopped while compiling after dependencies were downloaded. This leaves matching-source performance comparison **inconclusive**. See `docs/physics-lab/expansion-same-source-20261018.md` for exact paths, commands and blockers, and `scripts/engineering/physics-lab-20261018/compare-native.py` for a prepared same-executable comparison runner. There are no comparable GPU/CPU speed claims.
5. **Actual JS contact geometry improvement:** `src/core/physics.js` now uses the x-dependent front/back section radius for interior collisions against horizontal torso/shoulder ellipses, rather than projecting every point to the full depth radius irrespective of horizontal position. The old projection could induce discontinuous side-wall displacement between adjacent cloth vertices. `node scripts/check-avatar.mjs` still passes after the change. The three after-values for **peak local strain** are 154.9%, 93.5%, and 455.6% (previously 171.8%, 206.5%, and 836.5%). The modified upper-body fixture improved average strain 15.7% → 9.8% and mean seam gap 11.8 → 9.4 mm. `node scripts/check-avatar-torso-contact-regression.mjs` passes on its 1264 structural edges and 102 seam constraints. The remaining 455.6% local extension is physically unacceptable and remains an unresolved fitting defect; the new numerical guard is regression-only and not a calibration threshold.

`node scripts/check-ppf-fit-acceptance.mjs` also passes the existing all-frame IPC/strain/seam acceptance fixture. The separate historical `scripts/check-ppf-thomas-fit-tuning.mjs` could not run because `blender_bridge/output/ppf-fit-tuning-20261013/solver-report.json` is absent in this workspace. This is a missing historical test artifact, not evidence that the live PPF solver failed.

### Unresolved shoulder conflict in legacy simulation

The second diagnostic pass examined the ten highest stretched structural edges for the modified-body avatar. Eight of the ten lie in the shoulder region. The worst back-right shoulder edge joins particles 168→295: rest length **11.18 mm**, final length **62.12 mm** (455.6% extension). Particle 168 participates in the right-shoulder sewing endpoint, with a **36.0 mm** local seam gap and approximately **8 mm** seam rest spacing. Its normalized shoulder cap ellipse coordinate is **q=0.937** (inside the raw cap), whereas a nearby unsewn particle is **q=1.102** (outside); normalized neck ellipse q is above 4.8 and is not the direct cause. This supports a **shoulder-cap collision/sewing conflict** rather than a generic material coefficient deficiency. The next physics correction needs a better shoulder surface/normal-aware draping model and seam-compatibility analysis; forcing those points together with arbitrary stiffness or fixture-specific rules could introduce body penetration.

A read-only counterfactual contact experiment tested lateral correction variants without editing the shipped model. The bounded 8 mm lateral shoulder projection reduced the global modified-body peak to **265.07%**, mean seam gap to **9.283 mm**, and sampled maximum triangle intrusion from **3.855 mm to 1.793 mm** (sampled penetrating faces 8→6). Unrestricted lateral projection reduced peak to **212.25%** but worsened mean seam gap to **10.378 mm**; the 18 mm correction variant raised peak to **585.09%**. These are evidence of a collision/sewing interaction, not justification for adopting an arbitrary fixed correction limit. No shoulder-contact mode was changed in production.

**Additional avatar-compatibility evidence:** `scripts/check-avatar-shoulder-modes.mjs` exhaustively tests standard and modified bodies at 160/180/200 cm with default, limited and adaptive lateral shoulder contact (18 cases). The 8 mm lateral choice decreases the 180 cm modified-body peak from 455.6% to 265.07%, but increases 200 cm standard-body sampled max intrusion from 9.04 mm to **56.90 mm** and increases its peak strain from 93.45% to **173.24%**; it also worsens modified 160 cm strain 133.51%→264.99%. The adjustment is not broadly defensible. See `docs/physics-lab/shoulder-contact-mode-comparison.md`.

**Optional contact-assist evidence:** `scripts/check-avatar-shoulder-contact-matrix.mjs` runs 48 further cases: 160/180/200 cm, standard or modified proportions, seam midpoint stabilization on/off, optional triangle contact assist on/off, and optional continuous surface correction on/off, over 120 frames. On the modified 180 cm fixture with midpoint stabilization, enabling both assists can reduce peak strain 460.37%→203.60% and maximum sampled intrusion 5.34→1.92 mm. On standard 160 cm, that same setting instead worsens peak 93.93%→151.14%, maximum seam gap 17.21→29.72 mm and maximum sampled intrusion 21.96→38 mm. No single combination reliably improves both sewing and contact across sizes. The current continuous surface correction accepts improvements in sampled penetration without independently screening worsening strain or sewing closure. See `docs/physics-lab/shoulder-contact-assist-matrix.md`; the two matrices have different explicit option defaults, so their baseline numbers should not be conflated.

### Accepted-state contact diagnostic correction

Rust CPU and GPU VBD both previously published contact count and proximity from an earlier detection performed before the accepted cloth positions were committed. Source now recomputes the OGC contact set on accepted positions *before* committing State; the final count, term count and minimum separation describe those positions. Its profiling includes the extra detection. CPU final-state unconstrained gradient residual is also evaluated with that final contact set. This adds a detection cost to every step and should be included in wall-time comparisons. It does not independently prove absence of cloth/body penetration. New regression `tests/vbd_post_step_contact_metrics.rs` compares the published CPU result to a separately recomputed read-only final contact check; Rust VBD suite and numerical residual regression pass. Desktop-feature `cargo check --locked --offline --features desktop -j 2 --bin exo-session` passes. The GPU variant has compile-level verification, with runtime GPU comparison separately documented.

**Hardware validation:** `CARGO_INCREMENTAL=0 ~/.cargo/bin/cargo test --locked --offline --features desktop -j 2 --test gpu_post_step_contact_metrics -- --ignored --nocapture` completed successfully on the local arm64 Mac's Metal adapter. The independent accepted-state detection matched GPU-published contact count, term count and feature separation, while the pre-step separation differed as expected. The targeted Rust CPU VBD suite (4 tests), post-contact CPU test (1), and residual finite-difference contract (1) also passed.

### Source-level structural failure trace

`refreshSimulationAnalysis` now includes `quality.structural.worstStructuralEdges`, with up to ten ranked structural constraints and their stable particle and piece IDs, seam affiliations, original and deformed metric lengths, contact correction magnitudes, and percent extension. The underlying cloth/pattern state is unchanged by the diagnostic. `node scripts/check-avatar-strain-trace.mjs` validates the ordering, IDs, exact maximum correspondence and read-only behavior on the modified body fixture. The leading edge is `back:13 → back:140`, rest **11.18034 mm**, final **62.11797 mm**, attached to `seam-shoulder-r`.

## Native early-assembly behavior

The native T-shirt and dress begin with approximately **0.530 m** maximum seam separation because separate panels are initially arranged apart. With the baseline executable, the T-shirt gap decreases to roughly **0.447 m, 0.373 m, 0.331 m** across steps 1–3 (simulation time up to 50 ms). The dress similarly decreases to **0.446 m, 0.368 m, 0.330 m**. Repeat T-shirt physical traces matched exactly. These **early assembly transients** are unsuitable for labeling fit pass/fail or judging steady-state strain. The lab keeps `equilibriumEstablished:false` and `releaseGate:false` and treats the screening thresholds as diagnostics only.

A longer 20-step disposable CPU run, saved in `docs/physics-lab/settling-cpu-20step.json`, reached 0.333333 s of simulated time. The T-shirt maximum seam gap fell to **6.389 mm**, the dress to **9.124 mm**. Their step-20 extension p95 values were **18.389%** and **18.824%** respectively. Both repeated T-shirt traces matched. This demonstrates rapid initial seam closure and justifies measuring over the trajectory; it still provides no independently verified steady-state convergence or physical fabric calibration. Reproduction: `EXO_PHYSICS_STEPS=20 EXO_PHYSICS_OUTPUT=docs/physics-lab/settling-cpu-20step.json node scripts/engineering/physics-lab-20261018/run.mjs`.

The 40-step run (`docs/physics-lab/settling-cpu-40step.json`) reached **0.666667 s** simulated time. Maximum seam gap was **4.041 mm** for the T-shirt and **4.126 mm** for the dress; extension p95 was **11.430%** and **8.446%**, and extension max **34.436%** and **28.382%** respectively. The corresponding final CPU solve steps took approximately 453 ms and 892 ms end-to-end on this workstation in that execution. These are **individual samples**, not stable benchmark medians or a GPU speed comparison. A repeated T-shirt trajectory matched physical values and contact counts exactly. The convergence of the physical fit under independent sample measurements remains unverified. Run with `EXO_PHYSICS_STEPS=40 EXO_PHYSICS_OUTPUT=docs/physics-lab/settling-cpu-40step.json node scripts/engineering/physics-lab-20261018/run.mjs`.

The Rust ClothCraft checkout is ignored by EXO's outer Git repository. A portable source diff for the Rust CPU change is saved in `integrations/clothcraft/rust-patches/20261018-vbd-final-residual.patch` and its focused test in `integrations/clothcraft/rust-patches/vbd_residual_contract.rs`. ## Limits and next experiments

- Run longer settling and motion trajectories with explicit evidence of convergence. Use the same graded, closed-seam pattern and avatar fixture to distinguish bad initial 2D geometry, overstretched sewing constraints and solver contact behavior.
- Add an **independent** vertex/triangle and swept-cloth/body intersection audit for each simulated frame; `minimum_distance_m` from native OGC detection alone is not a penetration certificate.
- Record the accepted physics step timestep, contact terms, full wall time and convergence/gradient trajectory. Validate the seam penalty model with independent force-versus-displacement experiments and measured textile samples.
- Compare CPU and Metal GPU only after rebuilding both from the same source revision with identical solver settings, geometry, device metadata and warm-up. CPU f64 and GPU f32 may have different numerical trajectories; identical step counts alone do not establish equivalent physics. Never claim GPU acceleration from an unrelated binary or a backend label alone.
- Integrate passing validated physics into the exact revision-checked 2D-to-3D production document before marking the native project as independently fitted.

### Same-source arm64 CPU / Metal discrepancy

An arm64 desktop-feature build of the current Rust `exo-session` source successfully ran both CPU and GPU modes on the same local Mac (binary SHA-256 `97865bd21e75fdeff15aab3e4d8d8c665f7d24e93332219cda9d57e2e21f75ed`). The two modes used identical T-shirt geometry, 0.530 m initial seam gap, avatar, timestep and 16 iterations. Three-step reports are `docs/physics-lab/same-source-cpu-arm64.json` and `same-source-gpu-arm64.json`; automated screen `scripts/engineering/physics-lab-20261018/compare-cpu-gpu.mjs` writes `same-source-cpu-gpu-comparison.json`.

| Simulation step | CPU max seam gap | GPU max seam gap | CPU step wall | GPU step wall |
| --- | ---: | ---: | ---: | ---: |
| 1 | 447.49 mm | 524.61 mm | 327.5 ms | 57.0 ms |
| 2 | 373.47 mm | 518.24 mm | 407.0 ms | 35.7 ms |
| 3 | 331.48 mm | 511.84 mm | 509.0 ms | 40.3 ms |

The CPU closed approximately **198.52 mm** of initial seam separation over three steps; GPU closed **18.16 mm**. Their final gaps differ by **180.36 mm**, so the faster GPU timing **cannot** be interpreted as speedup at equivalent physical fidelity. The physical-parity screening gate is marked `BLOCKED_PHYSICAL_DIVERGENCE`. Device hardware timestamp queries were unavailable (`gpu_compute_ms:null`); wall time includes preparation, CPU OGC and readback and is a limited single-run observation.

The seam energy coefficients themselves appear equivalent between CPU (`src/vbd.rs`) and GPU packing (`src/gpu_vbd.rs`, WGSL kind 2). The biggest structural distinction is that CPU refreshes OGC detection when enough vertex movements hit their trust balls, about **17–18 detection passes per step** in this assembly fixture, while the GPU performs one initial detection followed by the final diagnostic detection, with **no in-solve radius/center refresh**. For the initial query radius 6 mm, the OGC trust-ball radius is around **2.7 mm**; the GPU's early seam gap drops roughly 5–6 mm/step, as expected if both sewn sides hit those original balls. CPU repeated conservative detection permits further progress over 16 iterations. GPU and CPU also differ in local Hessian regularization, line-search attempts and floating-point precision; confirming the separate effects requires GPU per-vertex reject/displacement traces. The physically defensible GPU fix needs staged OGC refresh and new contact-term/color buffers across bounded iterations, preserving the trust-region safety proof. Arbitrarily widening the ball would be unsafe. Keep GPU fit acceptance blocked until the solver paths pass same-source physical agreement and independent penetration checks.

**Immutable 40-step replay:** Concurrent Rust builds can replace the shared `target/debug/exo-session` with a CPU-only version, so subsequent work copied the GPU-capable executable to `.exo-build-scratch/physics-immutable-20261018/exo-session` and ran both paths with `EXO_PHYSICS_BINARY` set explicitly. These later runs used the same byte-identical arm64 executable SHA-256 `b3c2258e590d3bb794787f6e754e640c2f83db5cf6acfeb1de813c8057d137eb`. After 40 steps / 0.6667 s simulated time, maximum seam gaps were **4.041 mm CPU** versus **326.845 mm GPU**, a **322.803 mm** difference. CPU p95 extension was **11.430%**, GPU **6.228%**; GPU's low extension is not credible fit evidence while panels remain apart. Maximum vertex speeds were **0.321 m/s CPU** and **0.210 m/s GPU**, showing neither path is proved at rest. See `docs/physics-lab/immutable-40step-comparison.json`, `immutable-cpu-arm64-40step.json` and `immutable-gpu-arm64-40step.json`. An isolated engineering design exists at `.exo-build-scratch/physics-gpu-refresh-20261018T204719Z/GPU_OGC_REFRESH_PROTOTYPE.md`; the full staged GPU compute/readback/redetect/repack implementation remains unfinished. No experimental GPU solver update was promoted.

### GPU mid-iteration refresh engineering follow-up (experimental, no production release)

**Native workspace safety routing:** `integrations/clothcraft/workspace.mjs` now selects the f64 CPU physics backend by default even when macOS asks for GPU and the executable reports desktop capability. Hardware GPU physics is allowed only with an explicit research opt-in `EXO_CLOTHCRAFT_ALLOW_EXPERIMENTAL_GPU=1` *and* `EXO_CLOTHCRAFT_GPU=1` and actual native GPU capability. The reported workspace status distinguishes `gpuRequested`, `gpuSupported`, and actual `gpuActive`. `scripts/engineering/physics-lab-20261018/qa-workspace-gpu-guard.mjs` passes six selection cases. This source safeguard protects newly built launchers but **has not been deployed to the installed EXO app in this research run**. CPU default avoids exposing the demonstrated long-run GPU convergence defect as ordinary garment fitting. Never confuse hardware GPU availability with physically validated solver equivalence.

An actual isolated source prototype at `.exo-build-scratch/physics-gpu-refresh-20261018T204719Z/src/gpu_vbd.rs` now implements one GPU VBD iteration per chunk followed by readback, f64 OGC collision detection/recoloring and upload of updated contact terms, adjacency and movement balls. The implicit-Euler target, original velocity, timestep and prediction history remain fixed until the final accepted state. It **passes a real three-step hardware CPU/GPU seam comparison**, with maximum gap differences **0.466, 1.096 and 0.557 mm** against CPU on the mannequin T-shirt, improving substantially over the earlier 77–180 mm discrepancies.

**Safe production backend policy verified:** The native workspace adapter now checks both actual compiled desktop/GPU capabilities and an explicit research opt-in `EXO_CLOTHCRAFT_ALLOW_EXPERIMENTAL_GPU=1`, rather than treating the Swift launcher's default `EXO_CLOTHCRAFT_GPU=1` as proof of trustworthy physical equivalence. A real native session integration test (`scripts/engineering/physics-lab-20261018/qa-workspace-gpu-actual-session.mjs`) ran three isolated T-shirt opens successfully: GPU-capable binary under ordinary Swift-requested startup used CPU VBD; explicit opt-in used GPU VBD; and a CPU-only binary under explicit opt-in safely used CPU VBD. The default CPU route also ran one 1/60-second physical step and saved native state while preserving the 2D template byte-equivalent after JSON parsing. The six pure backend-policy combinations passed `qa-workspace-gpu-guard.mjs`. This is verified **source and isolated runtime behavior**, not a claim that a new macOS application bundle has been installed.

The same actual-session QA now additionally closes the CPU worker, starts a new worker, and reopens its saved project: the resulting 2D template, all 3D vertex coordinates and simulation clock match the accepted pre-save state exactly. The independent report validator (`scripts/engineering/physics-lab-20261018/validate-parity.mjs`) prevents fake equivalent-speed conclusions for mismatched executable/avatars, incomplete times, and unexplained backends; its focused synthetic test suite passes. These QA files exclusively use ephemeral `.exo-build-scratch` fixtures and never write to a user's saved garment.

However, **the 40-step test fails parity**: with the original conservative radius packing, GPU seam closure stalls at **169.422 mm** while CPU reaches **4.041 mm**. Diagnostic f64 minimum separations shrink toward **4.260 µm**, and the GPU inward packing allowance `16*f32::EPSILON*max(|local_center|,1)` consumes **1.907 µm** from every trust-ball radius. With default OGC relaxation around 0.45, that leaves only ~**0.010 µm** permissible radius at the late-stage contact; sample `docs/physics-lab/gpu-refresh-plateau-12step.json` and isolated `integrations/gpu-ogc-radii-results.txt` corroborate this. The first precision-aware packing experiment restores a larger mathematically allowable radius and retains post-readback f64 trust-ball checks, but its long run ultimately hits the existing **2 µm f32 separation safety floor** and aborts transactionally. Neither widening OGC radii nor disabling that guard is an acceptable repair. A robust hybrid fallback or numerically compatible contact update remains necessary before releasing this GPU solver.

`scripts/engineering/physics-lab-20261018/run-parity-immutable.mjs` provides a one-command immutable-executable acceptance gate; `tests/gpu_cpu_assembly_parity.rs` is an explicitly ignored hardware regression that fails on the original GPU kernel. An experimental GPU candidate MUST remain isolated while 40-step matching-physics and penetration checks fail. Faster GPU wall time is not a valid acceleration claim under physically divergent seam closure.

### Transactional GPU-to-CPU precision fallback prototype (research only)

An additional scratch experiment in `.exo-build-scratch/physics-gpu-refresh-20261018T204719Z/src/bin/exo-session.rs` snapshots the incoming native solver and `State` before attempting GPU VBD; when a GPU f32 precision guard rejects an intermediate candidate, it restores both and retries **the complete physical step** on the f64 CPU solver with the unchanged timestep, material, grab and original position/velocity. It publishes `actualStepBackend` (`GPU`, `CPU fallback`, or `CPU`) and cumulative `gpuCpuFallbackCount`, allowing QA to distinguish actual execution from the session's nominal `--gpu` flag. The report parser and per-step validator now reject invalid telemetry and prohibit GPU-only speed claims when any step used CPU fallback (9/9 focused tests pass).

Against the proper research mannequin (`assets/makehuman/mannequin.obj`) on the matched T-shirt, its three-step geometry remained near CPU (331.481 mm CPU vs 331.483 mm hybrid). At **12 steps**, however, CPU seam gap was **37.544 mm** versus **171.664 mm** hybrid with **3 CPU fallback steps**; at **40 steps**, CPU was **4.041 mm** versus **170.478 mm** hybrid with **24 CPU fallback steps**. Observed total 40-step wall time was approximately **22.15 seconds CPU** and **22.58 seconds hybrid**, without demonstrated equivalent physics. A prior scratch run reporting 156 mm CPU closure at 40 steps used a **different `public/makehuman-base.obj` avatar**, so that figure must not be compared to the research mannequin results. Three independent 12-step CPU replays of the original immutable baseline executable and avatar were bitwise repeatable through the reported seam metrics. The hybrid fails physical parity and is **not promoted** to production. See the scratch `CPU_FALLBACK_EXPERIMENT_REPORT.md` and `docs/physics-lab/parity-validator-20261018.md`.

**Isolated local-Newton instrumentation:** In the actual experimental Metal T-shirt solve, an instrumented workgroup shader reported **zero skipped Hessians over the first nine steps** (so the early `det <= 1e-20` discard is not the demonstrated source of the initial divergence), but hundreds of failed eight-attempt line searches and thousands of trust-ball projections. A controlled prototype with **10** line-search attempts instead of **8** decreased the 12-step hybrid seam gap only **171.664→171.573 mm** and worsened the 40-step result **170.478→170.866 mm**, versus unchanged CPU **4.041 mm** at step 40. The extra attempts are **not a validated solution** and were not integrated. Zero/near-zero f32 movement bounds and contact/gradient handling remain major research gaps. Numerical synthetic CPU-only Hessian contract at `research/oss/clothcraft/tests/gpu_vbd_hessian_precision.rs` passes 4/4; it proves possible conditioning failure modes but not that they occurred in the earlier 3-step physical fixture.

The 8-attempt instrumented GPU run counted **3,922 failed local line searches** and **74,399 OGC candidate trust-ball projections** across the first nine accepted GPU steps, compared with **zero determinant skips**. These counts are *kernel invocations*, not unique vertices and not proof that a projected candidate violates collision bounds. The 10-attempt controlled version still failed long-run parity and was reverted. Detailed provenance, collision geometry and logs are in `.exo-build-scratch/physics-gpu-refresh-20261018T204719Z/GPU_LOCAL_NEWTON_PARITY_REPORT.md`. A credible next fix requires equal-state, equal-vertex f64 versus f32 local energy/gradient/curvature/accepted-step diagnostics; extrapolating from synthetic Hessian tests alone would be unjustified.
